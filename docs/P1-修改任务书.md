## 1. 总体目标与验收原则

1. **不引入新依赖**：仅使用标准库（`os`、`sys`、`logging` 不引入，保持现有 `log()` 手写实现）。
2. **不改变用户语义**：参数含义、文件名生成规则（除 P1-2 的修正外）、冲突判定策略保持不变。
3. **每项可独立验收**：6 项各有 1 组以上可执行的验收用例（见第 4 节）。
4. **可回滚**：所有改动集中在 4 个源码文件，`git checkout` 即可整体还原。
5. **回归不退化**：P0 修复后的「预览 → 执行 → 刷新」主链路必须仍然全部通过。

### 1.1 明确的非目标

- 不重写 UI，不调整布局。
- 不改 `code_sum.py`（历史单体版本，已被 `.gitignore` 忽略）。
- 不新增 `requirements.txt`、`.spec`、CI（属 P2）。
- 不改变"操作成功后不可撤销"的产品定位；P1-6 只补**可追溯性**。

## 2. 问题清单与修改方案

### P1-1 文件名长度校验用了 UTF-8 字节数

| 项 | 内容 |
| --- | --- |
| 现象 | 中文文件名约 84 个汉字（+ `.png`）就被判定"文件名过长"并禁止执行 |
| 证据 | 实测 `validate_output_name('测'×84 + '.png')` → `ok=False`，提示 256 字节超限 |
| 定位 | [helpers.py:94-96](../helpers.py#L94-L96) |
| 根因 | 用 `len(filename.encode('utf-8')) > 255` 判断。Windows（NTFS）与 macOS（APFS）的上限是 **255 个 UTF-16 码元**，不是 255 个 UTF-8 字节；一个汉字在 UTF-8 中占 3 字节，导致上限被压到约 83 字 |
| 方案 | 新增 `name_length_units()`：`os.name == 'nt'` 或 `sys.platform == 'darwin'` 时返回 `len(name.encode('utf-16-le')) // 2`，其余平台（ext4 等）返回 UTF-8 字节数；`MAX_NAME_BYTES` 重命名为 `MAX_NAME_UNITS`；错误信息改为"字符单元"表述 |
| 影响面 | 仅放宽 Windows/macOS 的误判；Linux 行为不变；非法字符、结尾空格/点、系统保留名检查不变 |
| 验收 | 84 个汉字 + `.png` 通过；128 个汉字 + `.png`（132 码元）通过；`'测'×252 + '.png'`（256 码元）被拒 |

### P1-2 文件名前缀的首尾空格被写进文件名

| 项 | 内容 |
| --- | --- |
| 现象 | 前缀填 `" photo "` 时生成 `" photo _1.png"`（前导空格 + 空格下划线），Windows 上易与隐藏文件混淆、部分工具处理异常 |
| 证据 | 实测 `build_new_filename('1', ' photo ', 'png')` → `' photo _1.png'` |
| 定位 | [helpers.py:184-190](../helpers.py#L184-L190) |
| 根因 | `prefix_stripped = prefix.strip()` 只用于判空，拼接时仍用原始 `prefix` |
| 方案 | 拼接改用 `prefix_stripped`；判空逻辑不变（全空格前缀仍不生成下划线） |
| 影响面 | 只有含首尾空格的前缀会变化；中间空格（如 `a b`）保持不变 |
| 验收 | `' photo '` → `'photo_1.png'`；`'  '` → `'1.png'`；`'a b'` → `'a b_1.png'` |

### P1-3 TOCTOU 检测粒度过粗

| 项 | 内容 |
| --- | --- |
| 现象 | 预览后目录被外部改动，执行时可能漏检：mtime 变化小于 1 秒不报；文件内容被替换但 mtime 被还原时不报 |
| 证据 | 实测：snapshot mtime +0.6s → `changed=False`；内容替换后 `os.utime` 还原 mtime → `changed=False` |
| 定位 | [main.py:688-729](../main.py#L688-L729)（`_detect_directory_changes`）、[main.py:676-686](../main.py#L676-L686)（`_compute_signature`）、[main.py:464-475](../main.py#L464-L475)（`refresh_file_list`） |
| 根因 | ① 快照只记录 `st_mtime`（秒级浮点），比较时又用 `abs(diff) > 1.0` 容差；② 未记录文件大小，内容替换无法识别 |
| 方案 | ① `refresh_file_list` 采集 `st_mtime_ns` 与 `st_size`；② `_compute_signature` 改用 `(name, mtime_ns, size)`；③ `_detect_directory_changes` 比较 `(mtime_ns, size)` 二元组，去掉 1 秒容差 |
| 影响面 | 预览签名更敏感（文件被 touch 也会使预览失效，属预期行为）；性能不变（仍为一次 `os.stat`） |
| 验收 | mtime +0.6s → 检出；mtime 还原但 size 改变 → 检出；文件被改名 → 检出 `added`/`removed`；完全未变 → 不检出 |
| 已知边界 | 若外部程序同时还原 mtime **且**保持文件大小不变，仍无法检测（不引入哈希是刻意的性能取舍，写入任务书备案） |

### P1-4 进度条倒退且暴露内部临时名

| 项 | 内容 |
| --- | --- |
| 现象 | 进度条走满 100% 后归零重新走到 100%；阶段 1 的进度文本显示 `.__rn_tmp_xxxxxxxx__00003` 这类内部临时名 |
| 证据 | 阶段 1、阶段 2 各自以 `1..total` 回调（[file_ops.py:63](../file_ops.py#L63)、[file_ops.py:97](../file_ops.py#L97)），`ProgressDialog` 的 `maximum=total`（[dialogs.py:197-201](../dialogs.py#L197-L201)） |
| 定位 | `file_ops.py`、`dialogs.py` |
| 根因 | 两阶段各自计算进度，没有合并为一次线性进度；阶段 1 回调传的是 `temp_name` |
| 方案 | ① 阶段 1 回调改传目标名 `new`（UI 不再出现临时名）；② `ProgressDialog.update()` 按 `overall_total = total × 2`、阶段 1 进度 `current`、阶段 2 进度 `total + current` 统一换算；③ 文案改为"阶段 1/2：x / 2N" |
| 影响面 | 仅 UI 显示；`progress_callback` 的参数语义（阶段号、阶段内计数）不变，其他调用方无需适配 |
| 验收 | 回调序列为 `(1,1..N)`、`(2,1..N)`；UI 进度单调递增到 `2N`；进度文本全程不含 `__rn_tmp` |

### P1-5 执行中关闭窗口无保护

| 项 | 内容 |
| --- | --- |
| 现象 | 重命名进行中，通过任务栏关闭主窗口会导致进程退出、守护线程被杀，文件可能停留在临时名状态且不回滚 |
| 证据 | 全项目无 `WM_DELETE_WINDOW` 注册（grep 结果为空）；工作线程为 `daemon=True`（[main.py:1042-1047](../main.py#L1042-L1047)） |
| 定位 | `main.py` 的 `__init__`（窗口初始化段）与 `_sc_quit`（[main.py:410-413](../main.py#L410-L413)） |
| 根因 | 未接管窗口关闭协议，`Ctrl+Q` 也直接 `root.quit()` |
| 方案 | ① 新增 `_is_rename_running()`（判断工作线程是否存活）；② 新增 `_on_close_window()`：运行中弹提示并阻止关闭，空闲时 `root.destroy()`；③ `__init__` 注册 `root.protocol("WM_DELETE_WINDOW", self._on_close_window)`；④ `Ctrl+Q` 改为运行中拦截 + 确认后 `root.destroy()` |
| 影响面 | 正常退出路径由 `quit()` 改为 `destroy()`（`quit()` 只结束 mainloop，窗口对象仍存在） |
| 验收 | 伪造存活线程时调用 `_on_close_window()` → 出现警告且窗口未销毁；线程结束后 → 窗口销毁；`Ctrl+Q` 在运行中给出状态栏提示且不退出 |

### P1-6 成功改名无记录、日志无轮转

| 项 | 内容 |
| --- | --- |
| 现象 | 重命名成功后日志只有"成功 N 个文件"，不记录 `旧名 → 新名`；日志文件在用户主目录无限增长 |
| 证据 | `_on_rename_complete` 记录整个 `result` 的 `str()`，成功时无映射信息（[main.py:1084-1092](../main.py#L1084-L1092)）；`log()` 直接追加（[helpers.py:60-69](../helpers.py#L60-L69)） |
| 定位 | `main.py`、`file_ops.py`、`helpers.py` |
| 根因 | ① `two_phase_rename` 未返回已完成的映射；② 日志写入无大小上限 |
| 方案 | ① `two_phase_rename` 成功时返回 `renamed_pairs: [(old, new), ...]`（失败/取消返回空列表）；② `_on_rename_complete` 改写为结构化摘要，并逐条写入 `RENAME old -> new`、回滚失败写 `ROLLBACK_FAIL ...`；③ `helpers.log()` 增加 `_rotate_log_if_needed()`：超过 2 MiB 时重命名为 `rename_debug.log.1`（覆盖旧备份） |
| 影响面 | 日志行格式新增两类前缀；返回值新增键（唯一调用方是 `main.py`，向后兼容） |
| 验收 | 成功改名后日志含 2 条 `RENAME`；预置 > 2 MiB 日志后调用 `log()` 生成 `.1` 且新日志从空开始；失败时日志无 `RENAME` 且有 `ROLLBACK_FAIL`（如有回滚失败） |

## 5. 风险、兼容性与回滚

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 签名更敏感导致预览频繁失效 | `mtime_ns` 精度高，任何 touch 都会使预览失效 | 属预期：宁可要求重新预览，也不误改文件 |
| 日志量上升 | 每个文件一行 `RENAME`，5000 文件约 300 KB | 2 MiB 轮转，保留 1 份历史 |
| 关闭保护误拦 | 线程已结束但队列未处理时会放行（`is_alive()` 为 False），不会阻塞正常关闭 | 以线程存活为唯一判据 |
| `MAX_NAME_BYTES` 改名 | 仅 `helpers.py` 内部使用，`code_sum.py` 自带副本不受影响 | 已确认无外部引用 |
| 平台差异 | Linux 仍按 UTF-8 字节；Windows/macOS 按 UTF-16 码元 | 按 `os.name`/`sys.platform` 分支，README 的"保守拦截"表述需在 P2 同步 |

**回滚方式**：

```powershell
git checkout -- main.py helpers.py file_ops.py dialogs.py
```

本次不改动任何配置文件、不新增依赖、不修改数据文件，回滚无残留。
